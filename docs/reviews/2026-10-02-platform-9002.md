## Verdict

The sign is working on its normal path and displayed the correct current LINX Route 2 departure during this review. Its module structure is reasonable, but **it is not ready for an unconditional accuracy/reliability sign-off**. Seven reproducible issues need attention: four high-priority passenger-information problems and three medium-priority resilience/empty-state problems.

This was a review, not an implementation or release. No application code, dependencies, schedules, environment settings, Firebase rules, or deployments were changed.

## Findings

### 1. High — old predictions remain labelled LIVE during an outage

**Locations:** `frontend/src/platform-departures/main.js:101-111, 244-278, 374-387`; `frontend/src/platform-departures/styles.css:182-190, 272-274`.

After a successful response, failures retain the rows and their `data-source="realtime"`. There is no ongoing freshness expiry or LIVE downgrade. The 30-minute cache limit is checked only when reading saved data at startup; it does not expire an already mounted board. Worse, the outage status is explicitly hidden on the installed small-screen layout.

**Reproduced:** the source and the downloaded production JS both retained a LIVE departure after 34 simulated minutes without a successful refresh. A 29-minute-old saved LIVE response remained LIVE another 31 minutes after startup. The error status existed but the compact CSS hides it. Eventually the countdown can become “Departure time unavailable” while the LIVE badge still remains.

**Impact:** passengers cannot distinguish a working sign from one repeating old predictions.

**Fix:** track the last successful response and prediction/evidence timestamps; downgrade/remove LIVE once evidence expires; retain scheduled information only within an explicit bounded policy; display a short visible “Updates unavailable” state inside the 320 × 80 board. Cache restoration must be visibly provisional, never immediately trusted as live.

### 2. High — delayed departures disappear after their scheduled time

**Locations:** `server/departures.js:12, 132-159, 476-477, 524-539`.

Schedule candidates are discarded more than 60 seconds after their scheduled departure **before** realtime predictions are applied. `mergeTripUpdates` can update existing candidates, but cannot restore a candidate already removed. The later selector correctly understands future predicted departures, but never receives the missing row.

**Reproduced:** a Route 2 trip scheduled for noon, with a fresh prediction of 12:10, vanished at 12:01:01. Collection and subsequent merging both returned zero rows for it.

**Impact:** the sign can advance to the next bus or report no departures while the delayed bus is still expected.

**Fix:** retain a bounded late-trip lookback, apply cancellations and predictions, then filter using the effective departure time. Add a complete aggregation regression test, not only a selector test with an already retained delayed row.

### 3. High — whole-trip cancellations without stop rows are lost

**Locations:** `server/gtfs-trip-updates.js:24-40`; `server/departures.js:179-223`.

A cancellation is noticed at trip level but emitted only while iterating stop-time updates. A valid whole-trip cancellation with no stop-time rows produces no parsed cancellation. The schedule therefore survives the merge.

**Reproduced:** `CANCELED` for the scheduled trip, with an empty stop-update list, parsed to `[]`; the cancelled departure remained in the output.

**Impact:** passengers can be directed to wait for a cancelled service.

**Fix:** preserve trip-level cancellations separately, keyed by trip and service date; apply them independently of stop rows. Test empty/absent stop lists and recurring trip IDs on different service dates.

### 4. High — NO_DATA can be promoted to LIVE without a prediction

**Locations:** `server/gtfs-trip-updates.js:28-38`; `server/departures.js:211-228, 313-363`.

The parser handles SKIPPED but not the NO_DATA stop relationship. An update with no time and no delay is then treated as a zero-delay prediction. A matching fresh vehicle can promote that scheduled time to LIVE despite the publisher explicitly withholding prediction data.

**Reproduced:** a Route 2 NO_DATA update with neither departure time nor delay, plus a fresh exact-trip vehicle, returned `departure_source="realtime"` and `live_evidence="trip_update_and_vehicle"`.

**Impact:** the sign claims a live prediction where only a scheduled departure exists.

**Fix:** preserve NO_DATA and other relevant relationships; require an actual finite prediction time or explicit delay before marking a row predicted. Keep legitimate zero-delay predictions distinct from missing delay data.

### 5. Medium — a hung fetch stops all future polling

**Locations:** `frontend/src/platform-departures/main.js:315-348, 378-387`.

XHR uses a 15-second timeout, but the normal `fetch` path has no timeout or cancellation. The next poll is scheduled only after the current request settles. A never-settling request therefore stops refreshes indefinitely.

**Reproduced:** a pending fetch caused one request and zero scheduled future refreshes, in both source and production JS diagnostics.

**Fix:** provide a bounded fetch deadline and cancellation where supported; ensure late responses cannot overwrite newer state. Preserve the XHR fallback. Test a genuinely hanging request, not only an immediately rejected network request.

### 6. Medium — missing LINX schedule is reported as no scheduled service

**Locations:** `server/server.js:207-230, 826-830`; `server/departures.js:472-479`; `server/platform-departures.js:33-61`.

Schedule availability is checked across all terminal agencies, not for the requested platform's agency. If LINX metadata is missing but Barrie metadata exists, the terminal request succeeds and platform 9002 returns `no_departures`. The frontend displays “No departures scheduled.” The platform response also removes the terminal source-health information.

**Reproduced:** a service with Barrie trip metadata but no LINX metadata produced a successful platform response containing `status="no_departures"` and an empty list.

**Impact:** unavailable data is presented as confirmed absence of service.

**Fix:** validate required schedule coverage for the requested platform, preserve agency-specific health/freshness information, and distinguish `schedule_unavailable` from a valid empty schedule. Apply similar checks to expired service coverage.

### 7. Medium — the one-hour window gives a misleading empty message

**Locations:** `server/departures.js:11, 132-159, 429-459`; `frontend/src/platform-departures/main.js:250-253`.

The platform endpoint uses the terminal board's one-hour window. If the next bus is further away, the sign says “No departures scheduled,” without explaining that only the next hour was searched.

**Reproduced using the current published schedule:** at 4:00 a.m. Toronto time on Monday, October 5, the one-hour result was empty, but the next departure was at **5:30 a.m.**

**Fix:** give individual platform signs a bounded next-departure search independent of the terminal board's window, or explicitly say “No departures in the next hour.” Include overnight and weekend-to-weekday boundaries.

## Structure, security, and lower-priority observations

**Sound foundations:** the view is small and independent; server-side platform filtering is centralized; stop validation is bounded; text uses DOM `textContent` rather than untrusted HTML; branding assets are allowlisted; unchanged rows are not repainted; polling is serial; XHR/storage/Intl fallbacks exist; the LINX handoff rejects ambiguous multiple-vehicle matches.

**Structural improvements:** keep source/evidence timestamps and trip identity in the platform payload, rather than collapsing it to time and source label. Share client/server stop-range definitions. Filter by platform before applying a terminal-wide row cap if services expand. A platform-2 request currently invokes all terminal agencies and the combined vehicle service; agency-specific aggregation or a shared bounded result cache would reduce unnecessary work. No load test or Vercel billing audit was performed.

**Security:** no critical sign-specific injection, secret exposure, or arbitrary upstream-fetch path was found in the reviewed path. Validation and deployed CSP were checked. An auxiliary LINX trip-update URL in `vercel.json:149` uses HTTP, even though the HTTPS endpoint works; use HTTPS consistently for externally supplied evidence. Public API abuse/rate limits and platform infrastructure controls were not comprehensively penetration-tested. This sign has no Firebase authentication or write path; Firestore/Storage rules and indexes are not applicable to this review.

**Minor date wording:** `main.js:165-167` identifies tomorrow by adding 24 hours. Across the November 1 fall-back transition, a November 2 departure can be labelled by weekday instead of “tomorrow.” The departure timestamp remains unchanged, so this is a wording issue. Use Toronto calendar-day arithmetic.

**Operational assumptions:** exact inbound-to-outbound vehicle continuity is inferred because LINX static metadata has no block assignment. A unique nearby inbound candidate is useful evidence, but not dispatch confirmation. Confirm the currently assigned physical bay and the intended policy for LIVE evidence with operations.
